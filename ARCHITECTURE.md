# Architecture

Implementation notes for contributors. Conventions and commands live in `AGENTS.md`; user-facing documentation lives in `docs/`.

## Sandbox

The agent's shell runs inside a **just-bash** virtual filesystem. `AGENT_WORK_DIR` is mounted at `/home/user/work` and skills at `/home/user/skills`. File operations within the sandbox are real (they read/write the actual `AGENT_WORK_DIR` on disk), but the agent cannot access anything outside the mounted paths.

Built-in programs: `skill` (subcommands: `read <name>`, `list`), `push` (available when a session ID is set; sends content to the chat UI). Extension skills can register additional programs via `registerProgram`.

## Job Queues

All queues use **bunqueue** (SQLite-backed) via the `ManagedQueue` abstraction (`src/queue/`). Default config: single concurrency, no auto-removal, 5-minute lock duration, stall detection disabled. Core queues: **Agents** (general prompt jobs) and **Chat** (conversational, streamed back via WebSocket). Job logs are persisted to SQLite (`src/queue/logStore.ts`); a timer purges orphaned entries every 6 hours.

## Workflows (DAG engine)

Workflows (`src/extensions/core/workflows/`) are directed acyclic graphs: a `steps` map (keyed by slug) plus an `edges` array (`from`, `to`, optional `branch`). The engine dispatches all root steps in parallel, then dispatches each successor once all its incoming edges are resolved (`satisfied` or `dead`, at least one `satisfied` — the join barrier). Control-flow nodes (`if`/`case`) are evaluated inline and mark their branch edges satisfied/dead; dead edges propagate to skip unreachable steps. Any step failure fails the whole run (fail-fast) and cancels in-flight jobs. Per-run edge states, step statuses, and results are persisted in SQLite.

`waitFor` nodes park their branch on a signal record (`workflow_signals`), one per waiting step of a run, so a signal ID is an instance-scoped address. All delivery paths (`POST /ext/workflows/runs/:runId/steps/:slug/signal`, `/signals/:signalId`, and the `emit` step) go through `deliverSignal` (`signalDelivery.ts`): run-active check, source check, `inputSchema` validation (`src/utils/jsonSchema.ts`), atomic claim, timer cancel, resume. `emit` only reaches waits with `scope: "broadcast"` (default is `instance`) and is narrowed by `correlate` (correlation key) and `targetRun`. Timeouts are re-armed at boot from `createdAt + timeoutMs`.

`humanTask` nodes (experimental, only with `HITL_ENABLED=true`; otherwise boot creates no HITL service, the portal API answers 503, `/portal/` is not served, the step fails validation, and the editor hides it) (`humanTask.ts`, registered in the coordinator like `waitFor`) create a portal task through `ctx.internal.hitl` (the `src/hitl/` service) and park on an instance-scoped signal with `source: "humanTask"`, which only `deliverSignal(..., { via: "hitl" })` may deliver. `humanTaskSource.ts` registers the `workflow` task source: answers resume the run, a manager cancel fails it, and the signal timeout hook expires the task (resuming with `outcome: "expired"` when `onTimeout: "expire"`). Any `workflow_failed` broadcast and run deletion cancel the run's open tasks. The step's output schema is built in (`humanTaskOutputSchema`).

`portal` triggers (portal workflow launchers, behind `HITL_ENABLED` like the rest of the portal): a workflow with `trigger.type: "portal"` (no ref; optional `trigger.portal` with title, `accept`, `maxSizeMb`, `fileRequired`, `roles`, `fields` JSON Schema) is offered at `GET /api/portal/workflows` to accounts with `portal:start` (filtered by `roles`). `POST /api/portal/workflows/:name/start` (multipart `file` + `data`) saves the upload under `<WORK_DIR>/uploads/portal/<uuid>/` and dispatches with payload `{ file: {path,name,mimeType,size}|null, data, submittedBy, submittedAt }`. The run executes as the operator bound when the workflow was last saved via `PUT` (stored in `app_config` by `portalRunAs.ts`, never in the JSON5 file, which the sandbox can write); unbound or unusable bindings answer 409 and surface as a trigger warning. The workflows extension registers the provider (`portalLaunchers.ts`) through `ctx.internal.portal` into the core registry (`src/portal/`).

The `http-request`, `fail`, `noop`, `chunk`, `set-variables`, and `start-workflow` step types are provided by the `core-wf-steps` extension.

### Template Expressions

Workflow string fields, agent prompts, and `if`/`case`/`iterator` expressions support `{{...}}` template expressions resolved by `src/extensions/core/workflows/template.ts`. A body made only of path characters (`[A-Za-z0-9_$.-]`, `isPlainPath` in `shared/templateExpression.ts`) is a plain dot-path lookup (`{{ trigger.payload }}`, `{{ steps.fetch-mails.result.data }}`); anything else is an expression for the evaluator: operators (`{{ steps.vars.result.count + 1 }}`, comparisons, `?:`, `??`) and composable function calls (`{{ jsonEscape(stripDataUri(image.dataUrl)) }}`). Hyphens stay path characters, so subtraction needs spaces (`a - b`). Only the text inside the braces is evaluated; a non-finite numeric result (`NaN`, `Infinity`) is substituted as is, with a warning:

- **Built-in function registry** (`templateFunctions/`, one module per category plus `coerce.ts`, registry in `index.ts`): pure, total helpers (they never throw; unusable input yields `""`, `null`, `[]`, or `NaN`) in the categories math (`num`, `int`, `round`, `formatNumber`, ...), string, list (`count`, `sum`, `pluck`, `sort`, ...), logic (`if`, `choose`, `isEmpty`, ...), encoding (`toJson`, `parseJson`, `base64*`, `urlEncode`, ...), and date (`nowIso`, `today`, `formatDate`, `parseDate`, `addDays`, `diffDays`, ..., on date-fns + `@date-fns/tz`; offset-less input is local to the zone, results are ISO 8601 with offset; default zone `WORKFLOW_TIMEZONE`, else the server's). Field reads on data go through `ownProp` (own properties only), so data-supplied keys cannot reach `constructor` and friends outside the evaluator's sandbox. The valid-name set and each function's `category` come from the shared, pure metadata table `shared/templateFunctionMeta.ts` (a load-time assertion guards against drift), so the evaluator, the load-time validator, and the frontend autocomplete and picker (grouped by category) all agree on which functions exist. Namespace values win over functions of the same name in the evaluation scope; the validator warns about an iterator alias named like a function.
- **Namespaces**: beyond `trigger`/`steps`, expressions resolve `{{env.<VAR>}}` (environment variable), `{{secret.<KEY>}}` (encrypted vault secret, ACL-checked, decrypted at access), `{{var.<KEY>}}` (plaintext global variable from the `VariableStore` - no decryption, no ACL), and `{{run.id|workflow|createdBy|baseUrl|url}}` (the current run; fields in `RUN_TEMPLATE_FIELDS`, `shared/workflows.ts`; `baseUrl` is `publicBaseUrl()` from `src/config.ts`, `url` the run page). Missing variables and secrets are left literal with a warning; an unset allowlisted env var resolves to an empty string with a warning.
- **Sandboxed evaluation** (`templateEval.ts`): expressions are evaluated by `subscript` (Justin preset). Guarded namespaces (`secret`, `env`) are resolved (ACL/allowlist) only as plain references and never placed in the evaluated scope (an expression using them is rejected with a warning); `var` is exposed as a lazy null-prototype proxy backed by the resolver. Unresolvable paths, unknown functions, and parse errors leave the expression literal with a warning.
- **Load-time validation** (`dagTemplateValidation.ts`): parses every non-path expression with the evaluator's grammar (syntax errors are reported) and validates the paths it references under the same namespace rules, sharing the function-name allowlist so validation cannot diverge from evaluation. Warnings are advisory (surfaced non-blocking on the workflow list/detail API).
- **Output schemas**: path checks and autocomplete for `trigger.payload.*` / `steps.<slug>.result.*` use each node's schema, which comes from a hand-authored `outputSchema` shorthand (edited in the field builder, `FieldListEditor` shape mode) on the trigger or step (leaves `string`/`number`/`boolean`/`object`/`any`, nested maps, `[item]` arrays; compiled by `outputSchemaCompiler.ts`) or else from the built-in trigger / step-handler schema. The editor's *Output schema* panel can fill the shorthand from the newest run via `GET /ext/workflows/meta/infer-schema/:name` (`schemaSample.ts` + `shared/schemaInference.ts`).
- **Frontend autocomplete** (`frontend/src/lib/autocompleteEngine.ts`, `templateScope.ts`): the `{{...}}` editor offers namespaces and built-in functions (sourced from the shared metadata) in value positions, classifies path vs function-argument cursor context, and closes open call parentheses when completing a value inside a call.
- **Variable picker** (`VariablePickerPanel.svelte`, `lib/variablePicker.svelte.ts`): the "Available data" panel docked beside the step panel (header toggle, Ctrl+Shift+Space). The on/off state is kept in localStorage; the panel shows only while it has a target. Every field with `TemplateAutocomplete` registers itself as the insertion target on focus, and focus moving anywhere else outside the panel (except its header toggle) drops the target; the tree comes from `buildScopeTree` (`templateScope.ts`, walks `getSuggestions`, so it offers exactly what autocomplete offers, steps in execution order) and entries are inserted with `insertReference` (`autocompleteEngine.ts`).

## Extension System

The registry (`src/extensions/engine/`) discovers extensions via `Bun.Glob("*/index.ts")` and `Bun.Glob("core/*/index.ts")`, validates manifests with TypeBox, resolves dependencies (topological sort), and initializes them in dependency order with a scoped `ExtensionContext`. The full context API is documented in `docs/writing-extensions.md`.

At runtime an extension can report warnings with `ctx.status.setWarnings([...])` (in memory, cleared on deactivate, `[]` clears): they are returned as `ExtensionInfo.warnings`, broadcast via `extension_schemas_changed`, and shown in the settings as a banner plus an amber icon in the extension list. To act as a configured operator account (a "run as" setting), an extension uses `ctx.internal.identity` (`src/auth/identityApi.ts`): `listOperatorUsernames()` for the dropdown, `mintToken(username)` for a short-lived bearer token (logged with the extension name; null for unknown, disabled, portal, and `admin`/`system` accounts), and `registerOwnerCounter(kind, fn)` (namespaced per extension) so user deletion is refused while the account is still referenced.

Extension routes are not mounted on Elysia directly (Elysia cannot add routes after `listen()`). The web server mounts a fixed `/ext/*` catch-all that dispatches through `ExtensionRouter` (`src/web/extensionRouter.ts`); routes are added on registration and removed on deactivate/unload, so enabling, re-enabling, or hot-loading an extension at runtime takes effect immediately. The router parses the body per the route's `parse` option from a clone of the request, so handlers can still read `request` directly.

### Extension UI Pages

Extensions declare Svelte 5 pages in `manifest.ui.pages` (`{ id, title, entry: "ui/<Page>.svelte" }`), rendered at `/ext-page/<name>/<id>` (sub-paths allowed for in-page routing). On activation, `uiBuilder.ts` compiles each page with `Bun.build` + `svelte/compiler` into a browser ES module whose default export is `(target, palim) => unmount`, plus a stylesheet with the Tailwind utilities the extension uses (scanned from `ui/`, against `frontend/src/theme.css`). Output lives in `<DATA_DIR>/ext-ui/<name>/<hash>/` (hash of `ui/` sources, pages, UI kit, and the builder itself) and is served publicly with immutable caching from `/ext-ui/*`. Build errors are reported per page, never fail activation.

- Each bundle carries its own Svelte runtime, pinned to the root `svelte` package. Host and page share no stores or context; the page gets a `PalimHost` (`shared/extensionUi.ts`) as its `palim` prop: authenticated `fetch`/`json` (relative paths → `/ext/<name>/...`), `onEvent` (server pushes via `ctx.ui.emit()` → `extension_ui_event` WS message), `theme`/`page`/`i18n` stores, `user`, `navigate`, `notify`, `confirm`. The mount wrapper also puts `palim.i18n` into Svelte context under `Symbol.for("palim.i18n")`, which kit components (`kitI18n.ts`) and nested extension components (`useI18n()` from `@ext/ui`) read.
- `@palim/ui` resolves to `frontend/src/lib/extensionKit.ts`; core component sources are compiled into the bundle. `phosphor-svelte`, `bits-ui`, `clsx`, `tailwind-merge`, `tailwind-variants` resolve from the frontend without installation.
- For external extensions with a `ui/` directory, `externalDependencyResolver.ts` symlinks the core `svelte` into the extension's `node_modules` (after `bun install`). The Svelte language server picks its compiler via `node_modules` resolution, not tsconfig `paths`; without the link it falls back to non-runes mode and types child component props as `never`.
- The extension watcher rebuilds pages when files under an external extension's `ui/` change and broadcasts `extension_lifecycle` `ui_updated`; open pages remount.

### Extension Hub

`src/extensions/extension-hub/` installs external extensions from git repositories (one folder per extension with `index.ts` + a `package.json` named after the folder with a semver `version`; releases are tags `<name>@<version>`). Each source is a bare mirror in `<DATA_DIR>/extension-hub/repos/`; install records live in the DB (`ext_extension_hub_*`, migration `0018`), never in files. Trees are extracted with `git archive` into staging and renamed into `EXTERNAL_EXTENSIONS_DIR`; loading stays with the `ExtensionWatcher`, driven explicitly via `ctx.internal.extensions.sync(folder)` (back-to-back renames of one path may emit no chokidar events), which reconciles the folder at once (no debounce) and resolves with its confirmed state (`active`/`suspended`/`failed`/`unloaded`). The watcher decides from the folder's state, not the event type: a fingerprint (folder and `index.ts` inode, `index.ts` mtime) taken at load tells a replaced or edited tree from late or duplicate chokidar events, which change nothing. Updates swap sequentially (move out, confirm unload, move in, confirm load); an unconfirmed unload aborts before the new tree is moved in, a failed or timed-out load restores the previous tree and keeps its install record, and the old tree is deleted only once the new one is active. A periodic check (`checkIntervalMinutes`) fetches all sources and emits `updates_changed` (feeds the `extensionUpdateCount` nav badge). `registry.loadOne()` purges the extension directory's entries from Bun's module cache (`require.cache`) before importing, so reloads pick up changed sibling modules and `package.json`, not just `index.ts`. This has no effect under `bun --watch`/`--hot` (Bun keeps its own module registry there), so in `bun run dev` hub updates return a restart warning.

### Dynamic Schema Enrichment

Settings schemas and step-type config schemas can name providers resolved at request time: `dynamicItems` on an array property fills its `availableItems` (provider returns `string[]`), `dynamicDefault` on a string property replaces its `default` (provider returns `string`; empty keeps the static default). The registry is `src/web/dynamicProviders.ts` (`enrichSchema`); `GET /api/extensions/:name/settings` and step-type serialization call it. `ctx.dynamicItems.invalidate()` broadcasts `extension_schemas_changed` so clients refetch. Built-in providers: `all-queue-names` (error-analyzer), `workflow-names` (core-wf-steps), `datatable-names` (datatables).

## Internationalization (i18n)

The UI ships in English (source and fallback) and German; `SUPPORTED_LOCALES` in `shared/i18n.ts` lists them. A user's language is stored in `users.locale` (null = follow the browser, migration `0014`), set in the user menu (`PUT /api/auth/me/locale`) or by an admin in the Users & Roles dialog, and returned on the identity.

- **Runtime** (`shared/i18n.ts`): nested JSON catalogs addressed by dot keys, `{param}` interpolation, i18next-style plural suffixes (`key_one`/`key_other`) picked by `Intl.PluralRules` when a numeric `count` is passed (`{count}` is number-formatted), lookup order active locale → English → `params.default` → key. Pure, no state, so it is safe to bundle into extension pages.
- **Core UI**: catalogs in `frontend/src/locales/{en,de}.json`. `en.json` is bundled and its keys type `t()` (`CoreKey`); others load lazily. Components call `t("ns.key", params)` from `$lib/i18n.svelte`, which reads rune state, so templates re-render on a switch. `App.svelte` drives the locale from the identity and provides the kit context. Plain TS helpers use `translateCore`/`translateExtension`/`activeFormat` from `$lib/i18nCore` (English in tests), or take a `CoreTranslate` parameter.
- **Extensions**: catalogs in `<ext>/locales/<locale>.json`, loaded on activation (`localeLoader.ts`), reloaded by the watcher, served by `GET /api/i18n/:locale`, refetched on `extension_lifecycle` events (incl. `locales_updated`). Manifest/schema text stays English on the wire; the client translates it via reserved keys with the English as fallback: `description`, `nav.<route>`, `pages.<id>.title`, `settings.<prop>.title|description`, `secrets.<KEY>.description`, `secretGroups.<group>`, `steps.<type>.label`, `steps.<type>.description`, `steps.<type>.config.<prop>[.<nested>].title|description` (`tx()` in the host; `StepConfigForm` takes an `i18nScope`). Pages use `palim.i18n` (`$i18n.t`, `$i18n.format`), whose `t` falls back to core keys (`common.*`).

## Web Server, Auth, Rate Limiting

Elysia serves the built frontend as static files, the API under `/api/` (`src/web/routes/`), extension routes under `/ext/`, compiled extension UI under `/ext-ui/*` (public, content-hashed), the portal under `/portal/` (when built and `HITL_ENABLED`), and `WS /ws` for job state, chat streaming, workflow and extension lifecycle events.

Auth is always on: all `/api/` and `/ext/` routes (except login, health, and extension routes registered with `{ public: true }`, such as webhook receive) and the WebSocket require a per-user bearer token. Every user can read everything except other users' chat sessions; roles map to write/management permissions (RBAC). Accounts have a `kind` (`users.kind`, migration `0017`): `operator` (default) or `portal`. Portal accounts are fenced in `authCheck` to `PORTAL_PATH_PREFIXES` (`/api/auth/`, `/api/portal/`, `/api/i18n/`, `shared/auth.ts`), get no implicit reads in the ability, are refused the WebSocket (close `4003`), and may only hold roles whose permissions are all portal-safe (`hitl:*`, `portal:start`; built-in role `portal-user`), enforced by the guards in `src/auth/guards.ts`. See `docs/api-security-model.md`.

Rate limiting: authenticated requests are limited per token (1000/min), so a user's browser session and the internal token their agent jobs use get separate buckets; everything else is limited per client IP (60/min). Failed logins are additionally throttled per IP and per username with exponential lockouts (`src/web/loginThrottle.ts`). Behind a reverse proxy, set `TRUSTED_PROXIES` so the client IP is taken from `X-Forwarded-For`.

## Secrets and Variables

- **Boot-time env** (`.env` + optional `.env.keys`): loaded once via `dotenvx.config()` in `main.ts`; with `.env.keys` dotenvx decrypts `.env`, otherwise Bun's `.env` loading applies. Infrastructure config only, no ACL or audit.
- **SecretVault** (`src/secrets/`): SQLite, AES-256-GCM, per-row ACL with consumer pattern matching, every access audit-logged. Extensions use `ctx.secrets.get/set/delete/keys`, workflows `{{secret.KEY}}`. Requires `SECRETS_MASTER_KEY` (or derivation from `.env.keys`). See `docs/secrets.md`.
- **VariableStore** (`src/variables/`): plaintext global variables (`global_variables`, migration `0009`), no encryption, ACL, or audit; always constructed at boot. Workflows use `{{var.KEY}}`.
